# MASTER PROMPT 03 — INVESTIGATE LOW STEP-LEVEL ACCURACY
## HackerRank Orchestrate October 2026 — Ghost Data Still Exists

### Mission

Investigate the low public-benchmark step-level agreement before making any submission decision.

The latest audit reports:
- Public sample status accuracy: 32/32 (100%).
- Exact step-sequence agreement: 11/32 (34.38%).
- Exact full-case agreement: 10/32 (31.25%).
- Step-field accuracy: 67/193 (34.72%).

These are reported results that must be reproduced independently.

### Strict boundaries

1. Work only in the existing October challenge workspace.
2. Do not touch any September challenge project.
3. Do not submit to HackerRank.
4. Do not push, create commits, change Git remotes, or perform external actions.
5. Do not delete or rewrite the existing audit log.
6. Preserve the current `output.csv`, `code.zip`, and audit report as a baseline. Make backups before any modifications.
7. Do not weaken cutoff enforcement or add sample-specific hardcoding merely to improve benchmark agreement.

### Phase 1 — Reproduce the benchmark

Run the current solution against the official public sample.

Independently calculate and report:
- Status accuracy.
- Exact step-sequence agreement.
- Exact full-case agreement.
- Per-field accuracy for each step field.
- Step-count agreement.
- Missing, extra, reordered, and mismatched steps.
- The number of cases with zero, partial, and complete step agreement.

Confirm the comparison uses the correct sample input, sample output, and freshly generated prediction. Check case IDs before comparing rows.

### Phase 2 — Produce a case-by-case discrepancy table

For all 32 public cases, create a table containing:
- `case_id`.
- Expected status and predicted status.
- Expected step count and predicted step count.
- Exact sequence match: yes/no.
- First mismatching step or field.
- Expected evidence ID and predicted evidence ID.
- Preliminary discrepancy category.

Use these categories where appropriate:
- Missing resource discovery.
- Extra resource discovery.
- Incorrect identity resolution.
- Incorrect resource-to-subject association.
- Incorrect evidence selection.
- Evidence captured after the audit cutoff.
- Incorrect operation or phase.
- Incorrect state or deletion-status interpretation.
- Incorrect ordering.
- Incorrect handling of backup, replica, index, tombstone, restore, or active data flow.
- Public benchmark behavior not yet explained by the specification.
- Other, with explanation.

Do not assume the reason before examining the relevant evidence.

### Phase 3 — Investigate the cutoff explanation

The previous report suggests some expected steps rely on logs whose capture timestamps are later than the case's `audit_at`.

For every discrepancy attributed to a cutoff issue:

1. Identify the exact case and expected step.
2. Locate the evidence file and the corresponding entry.
3. Inspect `evidence_files.csv` and determine the authoritative `captured_at` timestamp.
4. Inspect the official rules describing evidence cutoffs.
5. Determine whether the evidence entry itself existed before the cutoff, whether only the export or snapshot was created later, and whether the specification permits using that evidence.
6. Distinguish evidence-content timestamps from evidence-capture timestamps. Do not treat them as interchangeable unless the official rules say so.
7. State whether the expected step is genuinely inconsistent with the specification, or whether the implementation is missing a valid interpretation.

Do not dismiss benchmark differences merely because a file's name or date looks later. Do not use future evidence if the official rules prohibit it.

### Phase 4 — Trace the entire expected step sequence

For each public case, independently trace:
- The identity resolved from the request.
- Historical identifiers and aliases, if relevant.
- All candidate resources associated with that subject.
- The evidence available at the audit cutoff.
- The applicable deletion rules.
- The expected findings.
- The remediation operations required by those findings.
- The verification operations and their evidence requirements.
- The required phase and operation ordering.
- The final status.

Use the official problem statement, `AGENTS.md`, `deletion_rules.csv`, and relevant evidence files as the source of truth.

The public sample output may be used as a benchmark for comparison, but must not be treated as evidence that a resource existed or that an operation succeeded.

### Phase 5 — Check whether the evaluator is measuring the right thing

Review the official instructions to determine exactly how output correctness is evaluated.

Report separately:
- What the official contract explicitly requires.
- What the public expected output demonstrates.
- What remains an inference.
- Whether step-level differences are likely to affect evaluation.

Do not claim that 100% status accuracy is sufficient unless the official evaluation criteria explicitly support that conclusion.

### Phase 6 — Fix only demonstrated root causes

Do not start broad refactoring.

For each confirmed implementation defect:
1. Describe the defect and its source-backed impact.
2. Identify the smallest general fix.
3. Explain why the fix does not violate cutoff rules or introduce unrelated resources.
4. Add a regression test.
5. Rerun the affected tests.
6. Rerun all 32 public cases.
7. Rerun all 518 evaluation cases and the existing validator.
8. Rebuild `output.csv` and `code.zip` only after the fix passes validation.
9. Repeat the clean-extraction test and determinism check.

If the discrepancy is caused by an ambiguous or apparently inconsistent benchmark requirement, do not silently modify the implementation to imitate it. Document the ambiguity and preserve the evidence.

### Phase 7 — Final report

Create `STEP_ACCURACY_INVESTIGATION.md` with:
- Reproduced baseline metrics.
- The 32-case discrepancy table.
- Root cause for each mismatch, where established.
- Source-backed analysis of cutoff-related differences.
- Confirmed defects versus unresolved ambiguities.
- Changes made and regression tests added.
- Before-and-after metrics.
- Results of full-dataset validation.
- Remaining risks and recommended next action.

### Required final decision

Choose exactly one:

- `READY FOR HUMAN REVIEW` — the discrepancies have been explained, confirmed defects fixed, and all required tests rerun.
- `NOT READY — CONFIRMED DEFECTS REMAIN` — one or more confirmed defects remain.
- `BLOCKED — SPECIFICATION OR BENCHMARK AMBIGUITY` — a material discrepancy cannot be resolved from authoritative rules and evidence.

Do not claim a perfect solution merely because the status accuracy is 100%. Do not submit anything. Finish by giving me the exact metrics, the most important findings, and the next action I should take.
